# 오픈채팅 마을봇 구현 기획서

작성일: 2026-10-21 · 상태: 구현 기준 초안

## 1. 목표와 확정 사항

햇빛마을20단지 오픈채팅방에서 봇을 호출해 사진을 게시물로 등록하고, 기존 게시물 DB를 조회해 질문에 답한다.

- 구현 파일은 저장소의 `kakaoBot/`에 둔다. 기존 웹 앱 연동 변경은 `front/`에 둔다.
- 운영 위치는 SSH 별칭 `ubuntu`의 OCI 서버다. 기존 웹 앱은 `/home/ubuntu/app/apart`에서 운영 중이다.
- 초기에는 새 테스트 오픈채팅방과 사용자의 방장 계정으로 검증한다. 이후 별도 봇 계정으로 교체한다.
- AI는 회사 Nginx 도메인을 통해 호출한다. OCI에서 회사 사설 IP로 직접 접근하지 않는다.
- 사진 분석은 Qwen2.5-VL 7B, 요청 해석과 답변 작성은 Gemma4 26B를 사용한다.
- Docker는 사용하지 않는다. 봇 서버는 OCI에서 Node.js·PM2로 직접 실행한다.
- 공식 카카오 채널 챗봇이 아닌 비공식 중계 방식이다. 카카오 수신 계층은 Docker 없이 메시지·사진을 받을 수 있는지 검증 후 확정한다. Iris는 Android가 필요하므로 서버 단독 실행 도구로 간주하지 않는다.

## 2. 전체 구성

```text
테스트 오픈채팅방
  ↕ 메시지·사진 / 답변
카카오톡 수신·전송 계층(실행 방식 미확정, Docker 제외)
  ↕ 내부 HTTP 이벤트 / 응답 전송
kakaoBot(Node.js + TypeScript)
  ├─ Qwen: https://gitlab.swempire.co.kr/qwen/
  ├─ Gemma: https://gitlab.swempire.co.kr/ollama/
  └─ 기존 웹 앱의 봇 전용 내부 API → PostgreSQL·업로드 저장소
```

봇이 앱 DB에 직접 쓰거나 로그인 쿠키를 흉내 내지 않는다. 웹 앱 내부 API가 기존 게시물 검증·이미지 처리·권한 규칙을 재사용한다. 기존 사용자용 등록 API와 봇 API는 공통 저장 함수를 사용해 규칙이 달라지지 않게 한다.

### 현재 확인된 환경

| 항목 | 확인 결과 |
|---|---|
| OCI | Ubuntu 24.04 ARM64, 메모리 약 11GB, 확인 시 디스크 여유 약 17GB |
| 카카오 수신 계층 | Docker 없는 OCI 단독 구동 방식 미확정. Android/Iris 또는 다른 클라이언트 방식의 적합성 검증 필요 |
| Docker | 사용자 요구로 설치·사용하지 않음 |
| Gemma | 회사 서버 `192.168.0.51:11434`, `gemma4:26b` 로드 확인 |
| Qwen | 회사 서버 `192.168.0.51:8501`, health에서 `Qwen/Qwen2.5-VL-7B-Instruct`, loaded=true 확인 |
| 외부 연결 | 사용자가 Nginx `/qwen/` 설정 저장 완료. OCI에서 HTTPS 접근은 미검증 |

`/ollama2/`는 현재 `/ollama/`와 같은 Ollama에 연결되므로 사용하지 않는다. 회사 Nginx의 허용 IP에 OCI의 실제 출구 IP가 포함되어야 한다. AI 프록시를 전체 인터넷에 공개하지 않는다.

## 3. 사용자 흐름

### 3.1 사진으로 게시물 등록

1. 사용자가 방에서 `@마을봇 등록`을 보낸다.
2. 봇은 해당 사용자에게 사진과 등록 요청을 보내달라고 안내한다.
3. 사용자가 사진을 올리고 `@마을봇 이 공고 등록해줘`처럼 요청한다. 사진을 먼저 올린 경우도 최근 5분 이내 같은 방·같은 발신자의 사진만 연결한다.
4. Qwen이 사진에서 제목·본문·날짜·시간·장소를 읽고, Gemma가 요청과 함께 기존 게시물 형식으로 구조화한다.
5. 필수 정보가 충분하고 검증을 통과하면 자동 등록하고 게시물 링크를 답한다.
6. 날짜 등 필수 정보가 부족하거나 서로 충돌하면 구체적으로 질문한다. 같은 사용자의 추가 답변을 반영해 등록한다.

사용자가 명시적으로 등록을 요청한 경우에만 저장한다. 일반 사진 업로드나 사진 내용 질문은 등록하지 않는다. 매번 승인 절차를 추가하지 않으며, 정보가 불충분하거나 중복이 의심될 때만 확인한다.

사진은 요청당 최대 6장으로 기존 앱 제한을 따른다. 대기 상태는 방 ID와 발신자 ID를 함께 키로 사용한다. 다른 사용자의 사진은 섞지 않는다. 등록 요청에 묶인 사진은 재사용하지 않는다. `@마을봇 취소` 또는 마지막 활동 후 10분 경과 시 미완료 요청을 폐기한다.

실제 멘션 메타데이터를 우선 사용한다. Iris가 해당 정보를 제공하지 않으면 `@마을봇` 문자열 접두어를 호출 방식으로 사용하고 이를 사용자에게 안내한다. 실제 멘션 지원 여부는 수신 이벤트로 검증한다.

### 3.2 기존 DB 조회와 답변

예: `@마을봇 오늘 푸드트럭 와?`, `@마을봇 단수 공고 언제까지야?`

1. Gemma가 질문을 검색어·분류·날짜 조건으로 해석한다.
2. 앱 내부 검색 API가 허용된 조건만 받아 공개 게시물을 조회한다.
3. 오늘 일정과 현재 회차의 현장 제보를 구분해 결과를 만든다.
4. Gemma가 조회 결과 안에서만 짧게 답하고 근거 게시물 링크를 붙인다.

일정상 방문 예정인 것과 실제 도착 제보는 별도로 표현한다. 공고 게시 기간과 공사·단수 실제 일정도 구분한다. 자료가 없으면 확인 가능한 자료가 없다고 답한다. 모델의 일반 지식으로 마을 현황을 채우지 않는다. 모든 날짜 기준은 한국 시간이다.

## 4. 게시물 데이터와 기존 앱 연동

| 항목 | 구현 기준 |
|---|---|
| 분류 | FOOD(먹거리), NOTICE(공고), MARKET(장터) |
| 제목·본문 | 기존 검증에 따라 제목 15자, 본문 500자 이내로 요약 |
| 공고 | 공고 시작일·종료일 필수. 사진 속 실제 행사·공사 일정은 본문에도 보존 |
| 먹거리·장터 | WEEKLY 또는 ONCE, 요일·날짜·시간은 기존 스키마 준수 |
| 위치 | 명확한 좌표가 없으면 null. 사진에 없는 지도 좌표를 생성하지 않음 |
| 사진 | 기존 WebP 처리와 업로드 소유권 검증을 재사용해 저장 |
| 작성자 | 웹 앱의 전용 봇 사용자. 테스트 방장 계정과 앱 작성자 권한은 분리 |
| 삭제·숨김 | 기존 웹 앱 관리 기능 사용. 봇에서 수정·삭제는 초기 범위 제외 |

봇의 카카오 로그인 계정이 바뀌어도 기존 게시물 작성자와 처리 이력은 유지한다. 오픈채팅 참여자를 웹 회원으로 자동 가입시키지 않는다.

사진의 원문·사용자 요청·추출 결과를 구분한다. 연도를 알 수 없는 날짜나 판독 불가 문자는 추측하지 않는다. 제목·본문 제한 때문에 핵심 일정이 손실되면 등록 전에 추가 설명을 요청한다.

## 5. 중계와 처리 규칙

- 허용한 방의 봇 호출만 처리한다. 자기 메시지는 무시해 반복 답변을 차단한다.
- 실제 발신자 ID로 상태를 관리한다. 닉네임만으로 사용자를 식별하지 않는다.
- 외부 이벤트의 사진 URL·파일은 신뢰하지 않는다. 크기·형식·실제 이미지 해석 여부를 검사하고 허용된 미디어 경로만 읽는다.
- 사진 내부의 명령문과 사용자 입력은 데이터로 취급한다. 시스템 지시·DB 접근 권한을 바꿀 수 없다.
- 모델은 SQL을 실행하지 않는다. 검색 조건과 게시물 초안만 생성하고 서버가 검증한다.
- AI 요청은 초기 동시 처리 1건으로 시작한다. 대기 중에는 접수 응답을 보내고 순서대로 처리한다.
- 초기 제한은 사용자별 분당 요청 3건, 대기열 20건, 사진 1장당 10MB다. 초과 시 이유를 답한다.
- AI 호출 제한 시간은 180초다. 실패 시 게시물을 저장하지 않고 재시도를 안내한다.

### 중복·실패 처리

카카오 이벤트 ID를 포함한 요청 고유키를 영속 저장한다. 같은 이벤트가 재전송되면 기존 결과를 반환한다. 게시물 생성과 처리 완료 기록은 같은 DB 트랜잭션으로 묶어, 저장 후 응답 전송이 실패해도 재등록하지 않는다.

별개의 메시지로 같은 사진을 다시 등록하면 사진 해시와 최근 게시물 정보를 비교한다. 중복 후보 링크를 보여주고 같은 사용자가 재등록을 명시한 경우만 별도 요청으로 저장한다.

프로세스 재시작 후에는 영속 처리 기록으로 결과를 확인한다. 미완료 사진 대화는 초기 버전에서 복원하지 않고 다시 요청하도록 안내한다. 사진 임시 파일은 성공·취소·만료 시 삭제하고, 시작 시 남은 만료 파일도 정리한다.

## 6. API와 설정

### 회사 AI

- Gemma: `POST https://gitlab.swempire.co.kr/ollama/api/chat`
- Qwen: `GET https://gitlab.swempire.co.kr/qwen/health`
- Qwen 사진 분석: `POST https://gitlab.swempire.co.kr/qwen/describe`
- Qwen 글자 인식: `POST https://gitlab.swempire.co.kr/qwen/ocr`

Qwen은 기존 커스텀 multipart API다. 구현 전에 OpenAPI와 실제 응답을 확인해 입력 필드와 출력 형식을 확정한다. Ollama API와 같은 형식으로 가정하지 않는다.

### 웹 앱 내부 API(신규)

- 검색: 공개 게시물 검색 조건 → 게시물 ID·본문·일정·현재 회차 제보·링크
- 등록: 요청 고유키·검증된 게시물 초안·사진 → 게시물 ID·링크
- 처리 조회: 요청 고유키 → 진행·성공·실패 결과

경로는 기존 catch-all 라우팅 규칙을 확인해 구현 시 확정한다. 내부 API는 공유 비밀로 인증하고 외부 프록시에서 차단한다. 게시물 조회는 hidden/adminDeleted/userDeleted를 제외하며 사용자 개인정보·로그인 정보는 AI에 보내지 않는다.

### 설정 파일

`kakaoBot/.env.example`에는 아래 변수명과 설명만 둔다. 실제 비밀은 Git에서 제외한다.

| 변수 | 용도 |
|---|---|
| IRIS_BASE_URL | 내부 Iris 응답·조회 주소 |
| IRIS_WEBHOOK_SECRET | 중계 이벤트 인증용 비밀. Iris가 직접 인증을 지원하지 않으면 내부 전용 프록시에서 적용 |
| ALLOWED_ROOM_IDS | 테스트·운영 허용 방 ID |
| BOT_SENDER_ID / BOT_NAME | 자기 메시지 차단과 호출 대상 |
| GEMMA_BASE_URL / GEMMA_MODEL | 외부 Ollama 주소와 gemma4:26b |
| QWEN_BASE_URL | 외부 Qwen 주소 |
| APP_INTERNAL_URL / APP_BOT_SECRET | 기존 웹 앱 내부 API 연결 |
| APP_PUBLIC_URL | 게시물 링크의 공개 주소 |

ADB·Iris·웹훅·내부 API는 공인망에 직접 열지 않는다. Android 조작은 SSH 터널로 연결한다. 비밀번호·개인키·채팅 원문 전체를 로그에 남기지 않는다. 봇 호출과 관련된 사진·문장만 회사 AI로 전송하며, 테스트방 참여자에게 사진·요청이 분석 서버로 전달됨을 안내한다.

## 7. 파일과 운영 구성

```text
kakaoBot/
  기획서.md
  README.md                 # 설치·테스트·계정 교체·복구 방법
  package.json
  .env.example
  src/                     # 수신, 사용자별 대화 상태, AI 호출, 앱 연동
  tests/                   # 처리·인증·중복·정보 누락 검증
  deploy/                  # Android/Iris 배포 설정과 봇 실행 설정
```

새로운 대형 프레임워크 없이 Node.js·TypeScript로 구현하고 기존 PM2로 직접 실행한다. Docker 및 Docker 기반 Redroid 배포는 사용하지 않는다. 카카오 수신 계층은 아직 미확정이며, Android가 필요한 방식을 채택할 경우 Docker 없는 실행 가능성과 자원 사용량을 먼저 검증한다. 다른 런타임으로 이름만 바꾸어 컨테이너를 도입하지 않는다. 기존 앱 서비스를 중단하거나 기존 포트를 재사용하지 않는다.

계정 교체 시 Android 카카오톡 로그인과 테스트방 참여, BOT_SENDER_ID를 바꾸고 메시지·사진 수신을 다시 확인한다. 사용자 본인이 수행해야 하는 카카오 인증은 별도로 안내하며 인증번호를 저장하지 않는다.

## 8. 구현 순서와 단계별 완료 조건

### 1단계: OCI 연결과 Docker 없는 카카오 수신 방식 검증

OCI에서 Gemma 모델 조회·Qwen health·실제 사진 분석을 확인한다. Docker 없이 OCI에서 카카오 메시지·사진을 수신·전송할 수 있는 방식을 먼저 선정·검증한다. Iris를 채택하려면 별도 Android 실행 환경이 필요하다. 검증되지 않은 서버 단독 구동을 가능한 것으로 단정하지 않는다. 수신 환경이 준비되면 사용자가 테스트 계정으로 로그인한다. 테스트방에서 메시지 ID·방 ID·발신자 ID·멘션·사진 원본 수신·답변 전송을 검증한다.

**완료 조건:** 텍스트와 사진을 실제 방에서 받아 답변할 수 있음. 이 단계가 실패하면 게시물 연동보다 중계 문제를 먼저 해결한다. Android 로그인 차단 가능성과 사진 수신은 아직 보장하지 않는다.

### 2단계: DB 조회 답변

기존 일정·현장 확인 로직을 재사용하는 내부 검색 API와 Gemma 답변을 연결한다.

**완료 조건:** 오늘/특정 날짜/공고 질문에 근거 링크로 답변하고, 숨김·삭제 게시물은 노출하지 않으며 자료가 없으면 없다고 답함.

### 3단계: 사진 등록

Qwen 추출, Gemma 구조화, 정보 보완 대화, 사진 저장, 게시물 등록과 중복 방지를 연결한다.

**완료 조건:** 실제 테스트 사진이 사이트에 정상 표시되고, 일정 누락·다중 사용자·재전송·시간 초과에도 잘못된 등록이 발생하지 않음.

### 4단계: 운영 전환

재시작 복구와 임시 파일 정리, 요청 제한을 검증하고 운영 문서를 완성한다. 별도 봇 계정과 실제 방이 준비되면 허용 방 설정을 교체한다.

## 9. 필수 검증 시나리오

1. 정상 공고 사진으로 제목·본문·사진·날짜가 올바르게 등록된다.
2. 날짜 없는 공고는 질문하며, 추가 답변 전에는 등록하지 않는다.
3. 두 사용자가 사진을 연속으로 보내도 요청과 사진이 섞이지 않는다.
4. 봇 미호출·허용되지 않은 방·위조된 이벤트는 처리하지 않는다.
5. 같은 이벤트 재전송과 저장 직후 응답 실패에도 게시물은 하나다.
6. 기존 일정, 오늘 제보, 과거 회차 제보를 구분해 답한다.
7. 숨김·삭제 게시물과 계정 정보가 검색 답변에 노출되지 않는다.
8. AI 장애·잘못된 JSON·잘못된 날짜·이미지 다운로드 실패 시 저장하지 않는다.
9. 취소·만료·재시작 후 다른 요청에 이전 사진이 붙지 않는다.
10. 사진·본문의 지시문으로 내부 API 권한이나 조회 범위를 바꿀 수 없다.

자동 검증은 분기·보안·중복 방지 중심으로 작성한다. 통합 검증은 테스트방과 격리된 DB에서 수행하고, 실제 서비스 DB에 테스트 게시물을 무작정 생성하지 않는다.

## 10. 초기 범위 제외와 남은 불확실성

- 봇을 통한 게시물 수정·삭제, 외부 웹 검색, 전체 채팅 수집, 다중 마을 운영은 초기 범위에서 제외한다.
- Docker 없는 OCI 단독 카카오 수신 방식은 미확정이다. 기존 Redroid 배포안은 채택하지 않는다. 카카오 로그인·사진 원본 접근·실제 멘션 형식은 실기 검증이 필요하다.
- 방장 계정을 Android에 로그인할 때 기존 기기 로그인에 미치는 영향은 검증되지 않았다. 인증 과정에서 영향이 확인되면 사용자에게 먼저 알린다.
- 비공식 연동은 카카오 업데이트나 계정 제한으로 중단될 수 있다. Android 계층과 앱 처리 계층을 분리해 교체 범위를 줄인다.
- AI 사진 판독 정확도·회사 서버 응답 속도·OCI 외부 접근은 1단계에서 측정한다. 모델 설치나 회사 서비스 변경은 이 기획에 포함하지 않는다.
