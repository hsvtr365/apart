검토일: 2026-10-13 / 기준 커밋: `73c36eb`

이 저장소는 아파트 주민의 먹거리·요일장·공고, 지도, 현장 확인, 댓글과 카카오 계정을 제공하는 웹 앱이다. 단일 PM2 웹 인스턴스와 PostgreSQL, 약 1,700세대 단지의 소규모 이용을 기준으로 검토했다. 여러 서버로 확장해야만 생기는 문제를 현재 장애로 분류하지 않았다.

## 반드시 수정

### 1. [P1 · 재현] 내 정보에서 받은 댓글로 전환하면 로딩이 끝나지 않는다

- **역할/근거:** `front/src/components/account.tsx:23`의 활동 조회 effect와 `:42`, `:56`, `:61`의 loading 처리.
- **문제:** 내 글을 조회하는 동안 받은 댓글로 전환하면 이전 effect는 `active=false`가 된다. 새 effect는 `tab === "received"`에서 바로 반환하고, 이전 요청도 `setLoading(false)`를 하지 않는다. 실제 재현 결과 받은 댓글은 선택됐으나 로딩 마스크 1개가 계속 남았다.
- **최소 수정:** 조회하지 않는 분기에서도 loading을 해제하고, 탭별 요청을 취소하거나 요청 식별자로 관리한다. 받은 댓글 표시 여부를 다른 탭의 loading에 종속시키지 않는다.
- **미수정 영향:** 느린 네트워크에서 받은 댓글을 볼 수 없다. 탭 전환 중 응답 지연 회귀 테스트가 필요하다.

### 2. [P1 · 소스 분석] 빈 DB에서 정식 migration 순서로 설치할 수 없다

- **역할/근거:** `front/prisma/migrations/202610100002_notice_period/migration.sql:5`, `20261010090000_post_schedule/migration.sql:1`, `20261010100000_schedule_type/migration.sql:2`.
- **문제:** notice_period가 먼저 실행되면서 아직 생성되지 않은 `startDate`, `finishDate`, `weekdays` 등을 참조한다. README도 이를 명시하며 별도 검증 스크립트는 현재 스키마를 직접 구성해 우회한다.
- **최소 수정:** 기존 운영 migration 이력을 보존하면서 신규 설치용 기준 스키마와 이력 전환 절차를 마련한다. 빈 임시 DB에서 `prisma migrate deploy` 자체가 성공하는 검증을 추가한다. 이미 적용한 migration 이름만 임의로 바꾸면 안 된다.
- **미수정 영향:** 새 서버 설치·빈 DB 복구가 문서의 `npm run setup` 단계에서 실패한다. 현재 운영 DB가 즉시 고장난다는 뜻은 아니다.

### 3. [P1 · 소스 분석] 탈퇴·게시물 삭제와 동시에 진행 중인 쓰기 요청을 차단하지 못한다

- **역할/근거:** API `front/src/app/api/[[...path]]/route.ts:215`, `:483`, `:511`, `:517`, `:543`; `front/src/lib/account-retention.ts:129` 및 `:218`.
- **문제:** 프로필·좋아요는 계정 잠금 후 탈퇴 여부를 다시 확인하지만 글·댓글·업로드·현장 확인은 요청 초기에 읽은 user를 계속 사용한다. 인증을 통과한 요청이 지연되는 동안 탈퇴가 완료돼도 남아 있는 User 행을 참조해 저장할 수 있다. 게시물 공개/삭제 확인도 쓰기 트랜잭션 밖이어서 관리자 삭제 직후 대기 중 댓글이 저장될 수 있다.
- **최소 수정:** 실제 DB 쓰기 시 같은 계정 잠금과 탈퇴 재확인을 적용한다. 게시물 변경 가능 여부도 삭제 처리와 같은 잠금 또는 원자적 조건으로 검증한다. 긴 이미지 변환은 잠금 밖에서 하고 최종 저장 직전에 다시 검사한다.
- **미수정 영향:** 탈퇴한 계정의 새 활동이나 삭제 처리된 글의 새 댓글이 남는다. 동시 요청 순서를 제어하는 통합 테스트가 필요하다. 운영에서 경쟁 요청을 보내지는 않았다.

## 보강 권고

### 4. [P2 · 소스 분석] 상세·내 활동의 페이지 유지와 요청 취소 정책이 피드와 다르다

- **역할/근거:** `front/src/components/post-detail.tsx:28`, `:45`; `account.tsx:23`, `:70`; 비교 대상 `store.tsx:82`와 `:293`.
- **문제:** 상세는 `[id, data]`, 내 활동은 `[data, tab]` 변경마다 첫 페이지로 덮어쓴다. 댓글을 60개 읽은 뒤 좋아요를 누르거나 창에 재진입하면 다시 30개가 된다. 내 활동의 추가 조회 도중 탭을 바꾸면 이전 탭 응답이 새 탭의 rows에 들어갈 수 있다. 더보기에는 진행 중 잠금·취소·응답 유효성 검사가 없다.
- **최소 수정:** 피드처럼 읽은 페이지 범위를 유지하고 탭/게시물 키가 바뀐 응답을 버린다. 더보기 중 버튼을 잠그고 ID 기준으로 합친다. 상세 첫 로드와 갱신을 구분한다.
- **미수정 영향:** 읽던 댓글이 사라져 보이거나 다른 탭의 목록이 섞인다. 모든 목록을 거대한 공통 컴포넌트로 만들 필요는 없지만 요청 규칙은 통일해야 한다.

### 5. [P2 · 소스 분석] Windows와 Linux의 필수 설정 초기화가 다르다

- **역할/근거:** `pm2_start.sh:17`, `pm2_start.ps1`, `front/package.json`의 setup/serve, `front/src/lib/account-retention.ts:17`.
- **문제:** Linux는 `provision-abuse-secret.cjs`를 실행하지만 Windows 시작과 npm setup/serve에는 없다. `.env.example`의 빈 `ABUSE_HMAC_SECRET`을 그대로 둔 신규 환경에서는 빌드·공개 조회가 가능해도 카카오 로그인과 관련 계정 동작이 실패한다.
- **최소 수정:** 공통 시작 절차에서 기존 비밀값을 보존하며 초기화·검증한다. Windows에서 일일 보관기간 정리를 어떻게 실행할지도 문서에 명시한다.
- **미수정 영향:** 같은 소스인데 실행 경로에 따라 기능이 달라진다. 이미 키가 설정된 현재 운영 환경의 장애로 판정한 것은 아니다.

### 6. [P2 · 실측] 최신 현장 상태가 상세에서 명확하게 보이지 않는다

- **역할/근거:** `front/src/components/post-status.tsx:15`, `:30`; `front/src/app/globals.css:1585` 이후 상세 확인 버튼 규칙.
- **문제:** 날짜 버튼은 최신 보고의 `state`를 표시하지 않는다. `있어요`는 선택 여부와 관계없이 진초록이다. 운영에서 최신 상태가 GONE인 글을 열었을 때 있어요는 진초록, 없어요는 진회색으로 둘 다 강하게 표시됐다. 지난 회차 보고라면 현재 회차 버튼 선택도 없어 날짜만으로는 상태를 알 수 없다.
- **최소 수정:** 날짜 옆에 최근 기록의 있어요/없어요 상태를 함께 표시하고, 현재 회차 선택 표시는 체크·선택 배경 등으로 구별한다. 날짜 클릭으로 기록을 여는 동작은 유지한다.
- **미수정 영향:** “오늘 와요”라는 일정과 실제 “없어요”라는 제보를 혼동한다. 일정 상태와 실제 관찰 상태를 분리한다는 원래 요구가 시각적으로 약해진다.

### 7. [P2 · 소스 분석] 위치가 없는 사진 글에도 지도 버튼을 표시한다

### 8. [P2 · 소스 분석] 작성 중 일정 유형·분류를 바꾸면 입력한 일정이 유실된다

### 14. [P2 · 소스 분석/일부 실측] 글자·버튼·그림자 규칙과 가이드가 분리돼 있다

- **미수정 영향:** 같은 정보가 페이지마다 다르게 읽히며 작은 화면에서 가독성이 떨어진다. 단, 최근 요청으로 바뀐 사진 왼쪽 배치·작은 일정 태그·상태 색상 자체를 되돌리라는 뜻은 아니다. 아래 문서 정합성 표에 구별했다.

### 15. [P2 · 소스 분석] 썸네일 재사용이 홈에는 적용되지 않는다

### 16. [P2 · 소스 분석] 작은 사용자 동작이 전체 조회·정리 작업을 반복한다

## 가이드 자체의 갱신이 필요한 부분

기준 파일: `plan/UI-스타일가이드.md`. 이 폴더는 Git에서 제외돼 있어 새 개발 환경에서 동일 기준을 바로 확인할 수 없다는 점도 유지보수 제약이다.

| 가이드의 기존 내용 | 이후 요청/현 구현 | 처리 방향 |
|---|---|---|
| 피드 사진은 본문 아래, 작성자 먼저 | 사용자 요청으로 왼쪽 사진과 오른쪽 정보로 변경 | 최신 배치를 정식 가이드에 반영. 구현을 과거 배치로 되돌리지 않음 |
| 왔어요·갔어요 | 사용자 요청으로 있어요·없어요 | 문서·README 용어 갱신 |
| 360px 이하도 좌우 16px | 요청된 작은 화면 시안에 맞춰 피드 8px 적용 | 허용 조건을 가이드에 명시 |
| 일반 모서리 4px, 지도 말풍선 예외 | 상세 6px, 홈 카드 8px, 시간 선택 20px 등 추가 예외 | 의도된 예외만 승인된 기준으로 정리. 나머지는 공통값 사용 |
| 같은 정보·행동에 같은 스타일 | 상세 전용 헤더와 별도 입력 팔레트 추가 | 10~14번을 먼저 정리한 뒤 가이드와 구현을 함께 유지 |

가이드에 없는 최신 시안을 모두 “위반”이라 부르면 사용자가 승인한 변경까지 되돌리게 된다. **동작 오류 → 공통 조작·접근성 → 최근 의도 확인 → 문서 갱신** 순서가 맞다.

## 권장 진행 순서

1. 받은 댓글 로딩 고착, 빈 DB 설치, 탈퇴/삭제 동시 쓰기부터 수정한다: 1~3번.
2. 목록 추가 조회와 입력 초안 유지, 좌표 없는 지도 링크, 실행환경·테스트 차이를 정리한다: 4·5·7~9번.
3. 공통 input 선택자·터치 영역·모달 헤더부터 CSS 원본 블록을 통합한다: 10~13번. 최신 상태 표현은 6번과 함께 확인한다.
4. 가이드 문구를 최신 사용자 요구로 갱신하고 글자·버튼·그림자 규칙을 적용한다: 14번.
5. 홈 썸네일과 요청 범위를 개선하고 미사용 코드를 제거한다: 15~17번.

수정 후에는 320·390·720·1440px, 로그인/비로그인, 느린 응답 중 탭 전환, 댓글 31개 이상, 숨김/삭제 글, 지난 방문 회차를 검증한다. CSS 정리는 최종 계산 스타일과 스크린샷을 비교해야 하며 단순 문자열 검색만으로 완료 판단하지 않는다.
